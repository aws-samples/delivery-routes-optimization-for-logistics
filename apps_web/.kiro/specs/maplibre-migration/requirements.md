# Requirements Document

## Introduction

This document specifies the requirements for migrating the frontend map rendering stack from Mapbox GL JS to MapLibre GL JS with OpenFreeMap as the tile provider. The migration eliminates the proprietary `MAPBOX_TOKEN` dependency, replacing it with an open-source, API-key-free solution that provides equivalent map rendering capabilities for the route optimization web application.

## Glossary

- **MapLibre_GL**: The open-source map rendering engine (fork of Mapbox GL JS) used to display vector tile maps in the browser
- **OpenFreeMap**: A free vector tile service (tiles.openfreemap.org) that provides map styles and tiles without requiring an API key
- **react-map-gl**: A React wrapper library that supports both Mapbox GL and MapLibre GL via subpath imports (`/mapbox` or `/maplibre`)
- **MapComponent**: The main map view component displaying routes, warehouses, customers, geofences, and polygons
- **NextDayDeliveryMap**: A specialized map component for displaying a single delivery job's route and stops
- **PolygonMap**: A map component that renders a single polygon overlay (e.g., delivery zones)
- **MapPin**: A reusable marker component with popover details for displaying entities on the map
- **BackendStack**: The CDK stack responsible for deploying the frontend website bundle and runtime configuration to S3
- **Config_Schema**: The Zod-based validation schema for infrastructure configuration
- **appvars.js**: A runtime JavaScript file generated by CDK that provides configuration variables to the frontend application
- **MAP_VARS**: The centralized map configuration object in `appvars.ts` containing style URL and default coordinates

## Requirements

### Requirement 1: Map Rendering Without API Token

**User Story:** As a developer, I want the map to render without requiring a paid API token, so that the application does not depend on external paid services for basic map display.

#### Acceptance Criteria

1. THE MapComponent SHALL render an interactive map using MapLibre_GL without passing any access token prop
2. THE NextDayDeliveryMap SHALL render an interactive map using MapLibre_GL without passing any access token prop
3. THE PolygonMap SHALL render an interactive map using MapLibre_GL without passing any access token prop
4. WHEN the map initializes, THE MapLibre_GL engine SHALL load vector tiles from OpenFreeMap using the style URL defined in MAP_VARS.MAP_STYLE

### Requirement 2: Map Configuration

**User Story:** As a developer, I want centralized map configuration, so that all map components use consistent settings and the tile provider can be changed in one place.

#### Acceptance Criteria

1. THE MAP_VARS configuration SHALL provide a MAP_STYLE property containing a valid HTTPS URL to the OpenFreeMap liberty style
2. THE MAP_VARS configuration SHALL provide a DEFAULT_LATITUDE property set to 37.5577857 (Seoul station)
3. THE MAP_VARS configuration SHALL provide a DEFAULT_LONGITUDE property set to 126.9697484 (Seoul station)
4. WHEN a map component initializes without location-specific data, THE map component SHALL center on the default coordinates from MAP_VARS

### Requirement 3: Package Dependencies

**User Story:** As a developer, I want the correct packages installed, so that the application uses MapLibre GL instead of Mapbox GL for map rendering.

#### Acceptance Criteria

1. THE application SHALL include `maplibre-gl` as a dependency
2. THE application SHALL include `react-map-gl` as a dependency with MapLibre subpath support
3. THE application SHALL NOT include `mapbox-gl` as a dependency
4. THE application SHALL retain `@mapbox/polyline` as a dependency for polyline encoding and decoding

### Requirement 4: Import Consistency

**User Story:** As a developer, I want all map components to use consistent imports, so that the codebase uniformly references the MapLibre rendering path.

#### Acceptance Criteria

1. THE MapComponent SHALL import map primitives from `react-map-gl/maplibre`
2. THE NextDayDeliveryMap SHALL import map primitives from `react-map-gl/maplibre`
3. THE PolygonMap SHALL import map primitives from `react-map-gl/maplibre`
4. THE MapPin SHALL import marker primitives from `react-map-gl/maplibre`
5. WHEN a map component imports CSS styles, THE component SHALL import from `maplibre-gl/dist/maplibre-gl.css`

### Requirement 5: Map Feature Functional Equivalence

**User Story:** As a user, I want all existing map features to work after the migration, so that I can continue viewing routes, markers, geofences, and polygons as before.

#### Acceptance Criteria

1. WHEN route data with encoded polylines is provided, THE MapComponent SHALL decode and render route polylines on the map
2. WHEN warehouse data is provided, THE MapComponent SHALL display warehouse markers at the specified coordinates
3. WHEN customer data is provided, THE MapComponent SHALL display customer markers at the specified coordinates
4. WHEN geofence data is provided, THE MapComponent SHALL render geofence circles with the specified radius and position
5. WHEN polygon vertex data is provided, THE PolygonMap SHALL render a filled polygon overlay
6. WHEN segment and route data is provided, THE NextDayDeliveryMap SHALL display origin markers, destination markers, and the route polyline
7. THE MapPin SHALL render positioned markers with icon variants (house, person, face, restaurant) and display data popovers on click

### Requirement 6: Polyline Decoding Compatibility

**User Story:** As a developer, I want polyline decoding to continue working after migration, so that route visualization is unaffected by the map library change.

#### Acceptance Criteria

1. THE application SHALL use `@mapbox/polyline` to decode encoded polyline strings into GeoJSON geometry
2. WHEN an encoded polyline string is decoded, THE decoder SHALL produce valid GeoJSON LineString geometry compatible with MapLibre_GL source layers

### Requirement 7: Infrastructure Token Removal

**User Story:** As a DevOps engineer, I want the MAPBOX_TOKEN removed from infrastructure deployment, so that the system no longer manages or exposes an unnecessary secret.

#### Acceptance Criteria

1. THE BackendStack SHALL generate appvars.js containing REGION, USERPOOL_ID, USERPOOL_CLIENT_ID, and API_URL
2. THE BackendStack SHALL NOT include MAPBOX_TOKEN in the generated appvars.js content
3. WHEN CDK deploys the BackendStack, THE deployment SHALL succeed without a mapBoxToken value in the configuration

### Requirement 8: Configuration Schema Backward Compatibility

**User Story:** As a DevOps engineer, I want existing configuration files to remain valid after migration, so that deployments are not broken by the schema change.

#### Acceptance Criteria

1. WHEN a configuration file includes a mapBoxToken field, THE Config_Schema SHALL accept it as a valid optional string
2. WHEN a configuration file omits the mapBoxToken field, THE Config_Schema SHALL accept it as valid
3. THE Config_Schema SHALL continue to require all other mandatory fields (env, namespace, administratorEmail, fargateOptions, parameterStoreKeys)

### Requirement 9: Map Interaction Controls

**User Story:** As a user, I want standard map navigation controls available, so that I can pan, zoom, and reset the map view.

#### Acceptance Criteria

1. THE MapComponent SHALL provide a NavigationControl with zoom buttons positioned at top-left
2. THE NextDayDeliveryMap SHALL provide a NavigationControl with zoom buttons positioned at top-left
3. THE PolygonMap SHALL provide a NavigationControl with zoom buttons positioned at top-left
4. WHEN a user interacts with the map (pan, zoom), THE map component SHALL update the view state accordingly
5. WHEN a user clicks the reset view control, THE MapComponent SHALL return to the default center coordinates and zoom level
